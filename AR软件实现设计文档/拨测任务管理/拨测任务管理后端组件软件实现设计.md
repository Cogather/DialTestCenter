### 2.3 项目包结构设计

#### 2.3.1 OpenAPI Generator 使用说明

本项目采用 **OpenAPI Generator** 实现 API-First 开发模式，具有以下优势：

1. **接口先行**：通过 YAML 文件定义 API 接口规范，自动生成接口代码和数据模型
2. **统一数据模型**：各层（Controller、Service、DAO）使用同一套由 OpenAPI 生成的模型类，无需维护多套实体类
3. **避免命名冲突**：不再需要区分 `entity.TaskEntity` 和 `model.TaskEntity`，统一使用 `model.TaskEntity`
4. **文档自动生成**：API 文档与代码保持一致，降低维护成本

**代码生成流程**：
```
dialingtest-interface/src/main/resources/
├── task-api.yaml          → OpenAPI Generator → model.TaskEntity.java
├── template-api.yaml      → OpenAPI Generator → model.TemplateEntity.java  
├── callbacks-api.yaml     → OpenAPI Generator → model.CallbackRequest.java
└── ... (其他 YAML 文件)
```

**生成的内容**：
- **API 接口**：`TasksApi.java`、`TemplatesApi.java` 等，Controller 实现这些接口
- **数据模型**：`TaskEntity.java`、`TemplateEntity.java` 等，所有层共用
- **请求/响应对象**：`StartTaskRequest.java`、`TaskPageResponse.java` 等

**项目依赖关系**：
```
dialingtest-interface (接口定义项目)
    ├── src/main/resources/*.yaml    (OpenAPI 规范文件)
    └── 生成 → target/generated-sources/  (API 接口 + 数据模型)
                   ↓ (Maven 依赖)
dialingtest-service (服务实现项目)
    ├── Controller 实现 interface 项目生成的 API 接口
    ├── Service/DAO 使用 interface 项目生成的数据模型
    └── 无需维护额外的实体类
```

## 3. 子模块说明

### 3.1 任务/模板管理模块

* **功能职责**: 负责任务（`Task`）和模板（`Template`）的持久化数据管理（CRUD）。是整个组件的数据基础。
* **输入**:
    * `Controller`层转发的HTTP请求（如查询任务、创建模板）。
    * 其他`Service`层（如触发器、编排器）的数据读写调用。
* **输出**:
    * `model.TaskEntity` 或 `model.TemplateEntity` 数据（OpenAPI 生成的模型，供上层调用）。
    * 数据库的`INSERT`/`UPDATE`结果。

### 3.2 任务触发模块

* **功能职责**: 负责**创建“主任务”**（即 `5.3核心流程图` 流程的实例）。响应“定时”触发和“人工”触发，在任务表中插入新的主任务记录，并设置初始 `context` 状态。
* **输入**:
    * `TemplateJobScheduler`（定时模块）的调度信号。
    * `TaskController`（人工启动）的HTTP请求。
* **输出**:
    * 一条新的**主任务记录**（`model.TaskEntity`，OpenAPI 生成的模型），其 `context.step` 被初始化（如 `START_VALIDATION`）。

### 3.3 任务编排器模块 (流程引擎)

  * **功能职责**: 核心**流程引擎**。基于 Spring-Statemachine (SSM) 框架实现。本模块**不包含任何业务决策逻辑**（决策逻辑在 `config.StateMachineConfig` 中以 `Guard` 声明）或业务执行逻辑（执行逻辑在 `action` 包中实现）。
    1.  **创建与恢复状态机**: 响应 `TaskTriggerService` 的调用，创建新的状态机实例 (`StateMachine`)，或在服务重启、回调触发时，从数据库 `context.step` 字段恢复现有状态机实例。
    2.  **事件分发 (Event Dispatch)**: 作为状态机的“操作员”，负责接收外部事件（如 `CallbackController` 的HTTP回调或 `TaskImpl` 的完成信号），并将这些事件“喂”给（`machine.sendEvent()`）对应的状态机实例。
    3.  **持久化管理**: 依赖 `StateMachineListener` 将状态机的状态变更自动持久化回 `Task` 表的 `context.step` 字段，确保流程的持久性和可恢复性。
  * **输入**:
      * `TaskTriggerService` 的启动信号（用于创建状态机）。
      * `CallbackController` 的异步回调事件（用于驱动状态机）。
      * `Action` 中 `TaskImpl` 完成后发送的内部事件。
  * **输出**:
      * 调用 `StateMachine` 实例的 `sendEvent()` 方法。状态机将**自动触发** `Action` (如 `ValidationAction`)，并**自动决策**下一个状态。

## 4. 接口与数据模型

### 4.1 对外接口

本组件的对外接口均基于 HTTP/RESTful 协议，由 `controller.taskmanagement` 包实现。这些接口主要服务于三个目的：

1.  供 UDN 前端页面调用，实现人工任务启动、模板管理和状态查看。
2.  供“微调中心”等外部异步系统调用，以回调任务执行结果，驱动流程引擎。
3.  （部分接口）供其他内部微服务调用（如果需要）。

所有接口的 `path` 均以 `/dialingtest`（或 `.../taskmanagement`，取决于网关路由配置）为前缀。

#### 4.1.2 任务管理接口 (TaskController)

**1. 人工启动拨测任务**

  * **POST** `/dialingtest/tasks/start`
  * **功能**: 对应“人工触发”（`指定vpn启动拨测任务`），立即创建一个主任务并开始执行。

#### 4.1.3 外部回调接口 (CallbackController)

**1. 接收异步任务回调**

  * **POST** `/dialingtest/callbacks/notify`
  * **功能**: 接收“微调中心”等外部系统的异步任务完成通知（`8.12.1.1.4.6 - 2.c.i`）。
  * **请求体** (`dto.taskmanagement.CallbackRequest`):
    ```json
    {
      "async_job_id": "job-abc", // 对应 context 中的 async_job_id
      "status": "SUCCESS", // "SUCCESS" 或 "FAILED"
      "error_message": null, // 失败时的错误信息
      "result_data": { // 结果荷载 (可选)
        "model_name": "model-v1.2" // 例如模型训练的结果
      }
    }
    ```
  * **响应 (200 OK)**:
      * **说明**: 此接口会调用 `TaskOrchestratorService`。`Orchestrator` 根据 `async_job_id` 找到对应的主任务 *及其内存中的 `StateMachine` 实例（或从DB恢复）*。然后，它将 `status` (SUCCESS/FAILED) 转换为一个 `TaskEvent` (如 `EVENT_MODEL_TRAIN_DONE`)，并调用 `machine.sendEvent()`。**状态机（`StateMachineConfig`）将自动根据 `Guard` 决策下一个状态，并由 `Listener` 持久化。**


### 4.2 数据模型

本组件的业务逻辑强依赖于两个核心数据表，均存储于 PGSQL 数据库中。这两个表共同支撑了任务的触发、编排、状态流转和持久化。

#### 4.2.1 任务表 (Task Table)

* **(对应 `表8-16`)**
* **说明**: 这是“任务管理”组件的**核心状态机表**。它用于存储“主任务”（宏观流程，`main_task_id` = `id`）和“子任务”（具体执行动作，`main_task_id` != `id`）。主任务通过 `context` 字段驱动流程，子任务通过 `status` 和 `result` 反馈执行情况。

| 字段名 | 类型 | 约束 | 说明 |
| :--- | :--- | :--- | :--- |
| `id` | `bigint` | 主键,自增 | 任务唯一标识 (Task ID) |
| `main_task_id` | `bigint` | 索引, 外键 (自引用) | 标识所属的**主任务**（宏观流程）。主任务该字段等于 `id`。 |
| `parent_task_id` | `bigint` | 索引, 外键 (自引用) | 父任务ID。子任务该字段通常指向主任务 `id`。 |
| `creator` | `varchar(128)` | | 任务创建者（如用户名或 "CRON"） |
| `start_time` | `timestamp` | NOT NULL, 默认 `now()` | 任务创建（开始）时间 |
| `end_time` | `timestamp` | | 任务结束时间 |
| `status` | `varchar(16)`| NOT NULL, 索引 | 主任务的**宏观生命周期**状态 (`RUNNING`, `COMPLETED`, `FAILED`)。<br>1. 任务创建时设为 `RUNNING`。<br>2. 当 `StateMachineListener` 监测到状态机进入**最终状态** (如 `FINAL`) 时，将此字段更新为 `COMPLETED` 或 `FAILED`。<br>3. 此字段仅用于**快速查询**，不参与流程驱动。 |
| `result` | `varchar(16)`| | 任务的业务结果 ( `SUCCESS`, `FAILED` ) |
| `input` | `text` | | 任务输入参数 (JSON 字符串)，如拨测脚本、目标UE等。 |
| `output` | `text` | | 任务输出结果 (JSON 字符串)，如 `error_message`。 |
| `context` | `text` | | **[核心字段]** 仅用于**主任务**。存储 Spring-Statemachine (SSM) 上下文的 JSON 字符串。<br>1. **`context.step`**: (示例: `"START_MODEL_REPLAY"`) 存储SSM的**当前状态** (`TaskState` 枚举)。`StateMachineListener` 会在每次状态变更后自动更新此字段，用于状态机恢复。<br>2. **其他字段**: (示例: `"currentModelId": "m-123"`) 存储在状态机 `ExtendedState` 中的所有业务数据，用于在 `Action` 和 `Guard` 之间传递。 |
| `template_task_id` | `bigint` | 索引, 外键 (模板表) | (可选) 指示此任务实例是从哪个模板创建的。 |

### 4.3 核心流程

`taskmanagement` 组件的核心业务流程主要分为两大块：一是**任务的创建**（响应定时或人工触发），二是**任务的执行与编排**（驱动状态机流转）。

#### 4.3.1 任务创建流程 (人工/定时)

此流程展示了 `TaskTriggerService` 模块如何响应两种不同的触发方式（`TemplateJobScheduler` 定时触发 或 `TaskController` 人工触发），从而在 `Task` 表中创建一个新的“主任务”实例。

```plantuml
@startuml
title 任务创建流程

**流程说明**：
此流程是 `taskmanagement` 组件最核心的业务逻辑，完全由SSM事件驱动。

1.  **Action 执行**: 当状态机进入一个新状态（如 `START_MODEL_TRAIN`），SSM 框架会自动查找并执行绑定到该状态的 `Action`（如 `TrainModelAction`）。
2.  **异步等待**: `Action` 调用 `TaskImpl` 执行业务逻辑。如果任务是异步的（如调用微调中心），`Action` 会在 `StateMachine` 的 `ExtendedState`（即 `context`）中存入 `async_job_id`，然后 `Action` 执行完毕。此时，状态机“暂停”，停在 `START_MODEL_TRAIN` 状态，等待事件。
3.  **事件唤醒**: 当 `CallbackController` 收到外部回调时，它通知 `Orchestrator`。
4.  **事件分发**: `Orchestrator` 负责：
    a.  根据 `async_job_id` 找到对应的 `Task`。
    b.  从 `Task.context` 中恢复 `StateMachine` 实例。
    c.  将外部回调（`SUCCESS` / `FAILED`）翻译成一个 `TaskEvent`（如 `EVENT_TASK_DONE`）并调用 `machine.sendEvent()`。
5.  **自动决策与持久化**:
    a.  `StateMachine` (SSM 引擎) 收到事件后，自动查找 `StateMachineConfig` 中匹配的 `Transition` 规则。
    b.  它执行对应的 `Guard`（如 `isSuccessGuard()`）来判断决策。
    c.  决策成功后，它**自动将状态**从 `START_MODEL_TRAIN` 转换到 `START_MODEL_REPLAY`。
    d.  `StateMachineListener` 监听到此次状态变更，并**自动将新状态** `START_MODEL_REPLAY` **写回**数据库 `Task.context.step` 字段。
6.  **自动循环**: 状态机进入 `START_MODEL_REPLAY` 状态后，自动触发绑定到该状态的 `ReplayAction`，流程（第1步）重新开始。

## 5\. 状态机详细设计

### 5.1 概述

本组件的核心流程引擎基于 Spring-Statemachine (SSM) 实现。所有流程逻辑均在 `orchestration.config.StateMachineConfig` 中以“代码即配置”的形式声明式定义。

`TaskOrchestratorService` 仅负责创建、恢复和分发事件，`StateMachineConfig` 负责定义所有规则，`Action` 负责执行，`Listener` 负责持久化，实现了完美的职责分离。

本章详细定义了状态机所需的“状态”、“事件”以及“转换规则”的代码实现。

### 5.2 状态定义 (9状态模型)

`context.step` 字段采用“下一步要执行的动作”(Next Action)模型，共定义 9 个状态：

| `step` 状态值 | 对应的 `5.3核心流程图` 动作 | 触发的子任务/动作 |
| :--- | :--- | :--- |
| **`START_VALIDATION`** | `批量拨测任务 (验证场景)` | `DialingTestTask(type=validation)` |
| **`START_TRAINING_DIALING`** | `批量拨测任务 (训练场景)` | `DialingTestTask(type=training)` |
| **`START_PREPROCESS`** | `数据预处理/清洗` | **异步**调用“微调中心” (等待回调) |
| **`START_MODEL_TRAIN`** | `训练AI模型/生成检索库` | **异步**调用“微调中心” (等待回调) |
| **`START_MODEL_REPLAY`** | `新增样本/检索库回放` | `ReplayTask` (调用微调中心) |
| **`START_GRAY_VALIDATION`** | `灰度发布...` + `批量拨测...` (合并) | `GrayValidationTask` |
| **`START_FULL_REPLAY`** | `全量检索库回放` | `ReplayTask(type=full)` |
| **`START_WHITELIST`** | `批量拨测验证` (白名单) | `DialingTestTask(type=whitelist)` |
| **`START_FULL_RELEASE`** | `取消灰度` + `全量发布` (合并) | `FullReleaseTask` |
| **`FINAL`** | `Final` / `告警人工处理` | 流程结束（成功或失败） |

| | | | |
| `START_FULL_REPLAY` | `SUCCESS` (达标) | **`START_WHITELIST`** | `成功率判断(达标)` -\> 白名单验证 |

| `START_WHITELIST` | `FAILED` (有误伤) | **`FINAL`** (告警) | `成功率/是否存在失败(存在失败)` -\> `告警人工处理` |
