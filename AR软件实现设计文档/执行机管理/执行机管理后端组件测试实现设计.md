## 1. 总体设计

### 1.1 设计目标

- **职责分离**：  
  - `测试场景设计`：定义测试目标、步骤、验证点（WHAT）  
  - `测试实现设计`：定义测试代码结构、工具和实现方式（HOW）
- **最小重复**：业务流程、字段含义不在本文重复，只引用场景设计中的IT编号。
- **易实现**：为Python测试工程提供直接可落地的结构和示例。
- **可扩展**：新增IT场景时，只需要在两个文档中分别补充场景描述和实现方案。

### 1.2 技术栈与边界

- **语言/框架**：Python 3 + `unittest`
- **通信**：`websocket-client`（支持Text/Binary消息）
- **HTTP**：`requests`
- **数据库**：`psycopg2` 访问PostgreSQL
- **加解密/编码**：`hashlib`（SHA256）、`base64`、`binascii`（Hex）、`zlib`（CRC32）
- **测试运行方式**：命令行运行 `python -m unittest` 或 `pytest`（可选）

> 说明：Python测试工程作为黑盒集成测试，不直接访问Java代码，只通过WebSocket/HTTP/DB与后端交互。

## 3. 公共基础设施实现

本节描述所有测试类公用的工具与基类的实现思路，只给出关键接口签名和示例，不展开重复的细节。

### 3.1 BaseTestCase（`base.py`）

**职责**：
- 加载测试配置（`config.py`）
- 管理数据库连接（`db_helper`）
- 提供WebSocket客户端工厂方法
- 提供常用断言辅助方法（如 `assertExecutorStatus`）

**核心接口示例**（伪代码）：

```python
class BaseTestCase(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.config = load_config()
        cls.db = DbHelper(cls.config)

    def create_ws_client(self) -> "ExecutorWsClient":
        return ExecutorWsClient(self.config.wss_url, timeout=self.config.wss_timeout)

    def assertExecutorStatus(self, name: str, expected_status: int):
        row = self.db.get_executor(name)
        self.assertIsNotNone(row)
        self.assertEqual(expected_status, row["status"])
```

> 所有具体测试类均继承 `BaseTestCase`，避免复制连接/查询逻辑。

### 3.2 WebSocket客户端封装（`ws_client.py`）

**目的**：对 `websocket-client` 做一层封装，屏蔽底层细节，提供：
- `connect()` / `close()`
- `send_json()` / `recv_json()`
- `send_binary()` / `recv_binary()`

**关键点**：
- Text消息：统一为UTF-8编码的JSON字符串
- Binary消息：原始二进制，不做任何头部封装
- 超时：通过配置文件控制，避免测试阻塞

```python
class ExecutorWsClient:
    def __init__(self, url: str, timeout: int):
        ...

    def connect(self):
        ...

    def send_json(self, envelope: dict):
        self.ws.send(json.dumps(envelope))

    def recv_json(self, timeout: Optional[int] = None) -> dict:
        raw = self.ws.recv()
        return json.loads(raw)

    def send_binary(self, data: bytes):
        self.ws.send(data, opcode=websocket.ABNF.OPCODE_BINARY)

    def recv_binary(self, timeout: Optional[int] = None) -> bytes:
        frame = self.ws.recv_frame()
        return frame.data
```

> 实现细节（日志、异常包装）写在代码中，不在本文展开。

### 3.3 JSON信封处理（`json_message.py`）

**职责**：
- 保证所有发送的消息遵循通信协议设计中的信封格式：

```json
{
  "type": "RegisterRequest",
  "token": 1234567890123456,
  "payload": { ... }
}
```

**关键接口**：

```python
class JsonMessageHelper:
    def build(self, msg_type: str, payload: dict, token: Optional[int] = None) -> dict:
        env = {"type": msg_type, "payload": payload}
        if token is not None:
            env["token"] = token
        return env

    def parse(self, data: dict) -> Tuple[str, Optional[int], dict]:
        return data["type"], data.get("token"), data["payload"]
```

> 所有测试场景只关心业务payload，信封的构造和解析统一通过该工具类处理，避免重复代码与格式错误。

### 3.4 Binary编码工具（`binary_codec.py`）

**职责**：
- Base64编码/解码：challenge 字段
- Hex编码/解码：response、crc 字段
- SHA256计算：CHAP认证响应
- CRC32计算与验证：文件完整性

**核心接口**：

```python
class BinaryCodec:
    @staticmethod
    def encode_base64(data: bytes) -> str: ...

    @staticmethod
    def decode_base64(text: str) -> bytes: ...

    @staticmethod
    def encode_hex(data: bytes) -> str: ...

    @staticmethod
    def decode_hex(text: str) -> bytes: ...

    @staticmethod
    def crc32_hex(data: bytes) -> str: ...
    
    @staticmethod
    def compute_chap_response(sha256_hash_hex: str, challenge: Union[str, bytes]) -> str:
        """
        CHAP 摘要：SHA256(SHA256-Hash bytes + Challenge bytes) -> 64 字符十六进制。
        sha256_hash_hex: 数据库中的SHA256 Hash（64位十六进制字符串）
        challenge: Base64编码的16字节随机数（可以是字符串或bytes）
        返回: 64位十六进制字符串
        """
        ...
```

> IT-01（CHAP认证）、IT-03/05/06/11（crc字段）均依赖该工具，但具体业务含义在场景设计中，不在此重复。

### 3.5 文件分片工具（`file_chunks.py`）

**职责**：
- 将本地文件拆分为N个分片，用于脚本、APK、日志等下发
- 将收到的分片拼接为完整文件，用于日志/截图保存
- 为IT-11提供制造异常（缺失分片、乱序分片）的能力

**接口示例**：

```python
class FileChunks:
    DEFAULT_CHUNK_SIZE = 102400  # 100KB

    @staticmethod
    def split(path: str, chunk_size: int = DEFAULT_CHUNK_SIZE) -> List[bytes]: ...

    @staticmethod
    def join(chunks: List[bytes]) -> bytes: ...
```

> IT-10、IT-11 中会通过可选参数/辅助方法控制只发前N个分片或打乱顺序。

### 3.6 数据库访问工具（`db_helper.py`）

**职责**：
- 为测试提供只读或简单写入能力（如清理测试数据）
- 封装常用查询：`get_executor(name)`、`get_ues(executor_name)` 等

```python
class DbHelper:
    def get_executor(self, name: str) -> Mapping: ...
    def get_ues(self, executor_name: str) -> List[Mapping]: ...
```

## 4. 各测试场景的实现要点

本节只描述实现上的“关键点”和“特殊处理”，不再重复业务步骤；步骤细节请参见《测试场景设计》。

### 4.1 IT-01 / IT-08：认证与注销测试

**测试类**：`TestAuthentication`、`TestDeregister`  
**文件**：`test_authentication.py`

**实现要点**：
- 在 `setUp()` 中创建 `ExecutorWsClient`，在 `tearDown()` 中关闭连接。
- 成功注册场景：复用`BinaryCodec`进行Base64/Hex处理，构造正确的response。
- 失败场景：只修改username或response，复用同一流程。
- 注销场景（IT-08）：注册成功后发送 `DeRegisterRequest`，校验 `DeRegisterAck`，并通过 `DbHelper` 验证 `executor.status=0`。

**推荐测试方法**（示例）：
- `test_register_validUser_success()`
- `test_register_wrongPassword_fail()`
- `test_register_unknownUser_fail()`
- `test_deregister_afterRegister_executorOffline()`

### 4.2 IT-02 / IT-04：心跳与离线/重连测试

**测试类**：`TestHeartbeat`、`TestOfflineAndReconnect`  
**文件**：`test_heartbeat_offline.py`

**实现要点**：
- 心跳测试：使用循环发送 `ReportMsg`，每次之后用 `DbHelper` 验证 `last_online_time` 更新。
- 离线测试：  
  - 主动断开：调用 `ws.close()` 后，轮询数据库直到 `status=0` 或超时。  
  - 心跳超时：停止发送心跳，等待>90秒（可在配置中提供“加速模式”，用于自动化测试缩短时间）。
- 重连测试：新的 `ExecutorWsClient` 实例重新走 IT-01 流程，比较新旧token不相同。

**注意**：  
为避免实际等待90秒过长，可在实现中提供“心跳间隔/超时配置”，测试环境下使用缩短配置，与业务逻辑保持一致。

### 4.3 IT-03 / IT-09：任务下发与停止测试

**测试类**：`TestTaskExecution`、`TestTaskStop`  
**文件**：`test_task_execution.py`

**实现要点**：
- 任务下发测试：  
  - 测试代码扮演Agent，监听来自服务端的 `TaskStartRequest`。  
  - 收到请求后，构造 `TaskStartResponse` JSON（仅元数据），随后按场景设计发送Binary分片日志。  
  - 日志文件可以从 `test_files/` 目录读取，确保内容可重复。
- 任务停止测试：  
  - 在任务执行过程中（Binary分片发送中）触发TaskStop流程。  
  - 测试端需要同时监听TaskStop请求，并检查停止后是否还有新的任务分发（可通过DB或额外接口验证）。

**特殊场景实现**：
- “日志文件超大”场景：使用大于10MB的测试文件，通过 `FileChunks` 分片发送。
- “分片发送中断”场景：只发送前N个分片，然后不再发送，结合IT-11验证错误处理逻辑。

### 4.4 IT-05：UE管理测试

**测试类**：`TestUeAppList`、`TestUeAppInstall`、`TestUeScreenshot`  
**文件**：`test_ue_management.py`

**实现要点**：
- App列表查询：  
  - 模拟服务端发送 `AppListQuery`，测试端作为Agent返回 `AppListResponse`，或反向；具体方向遵循协议设计。  
  - 只需要在payload中构造若干 `app-item`。
- App安装：  
  - 使用 `FileChunks.split` 将APK/脚本拆分，按照“JSON信令 + Binary分片”的顺序发送。  
  - 不在测试层做ADB操作，ADB行为由Agent实现；测试只关注消息收发和结果。
- 截屏：  
  - 测试端扮演Agent，从本地PNG文件读取数据分片发送，模拟ADB截屏结果。

> 为避免与真实设备交互，建议：这些场景侧重验证协议和服务端行为，不模拟真实ADB，只使用静态测试文件。

### 4.5 IT-06：脚本更新测试

**测试类**：`TestScriptUpdate`  
**文件**：`test_script_update.py`

**实现要点**：
- 使用脚本测试文件（如 `.py` 或 `.zip`）生成 `filelen` 和 `crc`。
- 构造 `ScriptUpdateNotify` JSON信令，随后发送Binary分片。
- 验证服务端行为通过：  
  - 检查脚本文件在服务器上的存在（可通过REST/DB/文件系统辅助接口，视实际实现而定）。  
  - 或通过日志/操作记录表验证版本号更新。

> 和IT-05类似，测试重点为消息与文件传输，不模拟实际“脚本执行”。

### 4.6 IT-07：北向API测试

**测试类**：`TestNorthboundApi`  
**文件**：`test_northbound_api.py`

**实现要点**：
- 使用 `requests` 访问 `/api/executors`、`/api/executors/refresh`。
- 在 `setUp()` 中确保至少有1个已注册且在线的执行机（可复用IT-01逻辑提前准备，或通过固定测试数据）。
- 响应断言：使用JSONPath或直接dict访问校验字段。

### 4.7 IT-10：消息优先级队列测试

**测试类**：`TestPriorityQueue`  
**文件**：`test_priority_queue.py`

**黑盒验证思路**：
- 测试端作为Agent，记录收到的消息时间线。
- 场景：  
  1. 服务端开始通过某种触发方式（REST/DB预置数据）下发大文件（脚本更新）。  
  2. 当测试端已收到若干Binary分片后，触发任务停止请求（TaskStop）。  
  3. 测试端应在后续接收序列中看到：Text `TaskStopRequest` 出现在所有Binary分片之前（即插队）。
- 实现要点：  
  - 测试端对收到的每条消息记录 `(timestamp, type, size)`。  
  - 最终断言：`TaskStopRequest` 的 `timestamp` 早于部分后续Binary分片。

> 不需要直接访问Java内部队列，只通过网络行为验证高/低优先级策略。

### 4.8 IT-11：文件分片完整性测试

**测试类**：`TestFileIntegrity`  
**文件**：`test_file_integrity.py`

**实现要点**：
- 场景A（缺失分片）：  
  - 按正常流程发送JSON信令（声明 `filelen` 为完整大小）。  
  - 使用 `FileChunks.split` 获取分片，只发送前 `N-1` 个分片。  
  - 观察服务端行为：应在超时后标记失败，可通过REST/DB/日志进行验证。
- 场景B（CRC错误）：  
  - 正常分片数，但在发送前篡改某一分片内容或声明错误的 `crc`。  
  - 断言：服务端检测到CRC不一致，并给出错误状态。
- 场景C（乱序）【可选】：  
  - 故意打乱分片发送顺序，验证服务端行为（要求与通信层设计保持一致：要么支持乱序，要么明确报错）。
