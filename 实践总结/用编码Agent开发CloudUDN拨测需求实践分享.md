## 第二章：需求介绍 —— CloudUDN拨测系统的业务挑战

### 2.1 业务背景：分布式拨测系统的核心架构
CloudUDN 拨测平台是一个用于监测网络质量与应用体验的分布式系统。其核心架构主要包含两部分：
1.  **拨测控制中心**：负责任务管理、策略下发及数据汇总。
2.  **端侧拨测执行机**：分布在各地的物理设备（如 Android 手机、PC 等），负责接收指令、执行自动化脚本（如访问抖音、微信等应用）并上报测试数据。

### 2.2 本次实践需求：执行机通信协议的重构
本次编码 Agent 实践聚焦于**“执行机管理”**模块中的通信协议改造。
在早期的 V4 版本中，系统采用单条 WebSocket 连接同时承载信令和数据。当执行机上传大文件（如录屏视频）时，底层的 TCP 发送缓冲区会被占满，导致后续下发的“紧急停止”等控制指令被阻塞，无法及时送达。
为了解决这一问题，我们需要将原本的单链路架构重构为**双链路（Dual-Link）架构**，即在物理层面建立两条独立的 WebSocket 连接，分别传输控制信令和业务数据，确保高优先级的控制指令不会受大文件传输的影响。

## 第三章：实战回放 —— 编码Agent驱动“执行机双链接改造”全流程

### 3.1 辅助设计文档修改

#### 1. 输入
*   **原始需求**：CloudUDN拨测系统需要支持大文件（APK/脚本/日志/截图）的高效传输，同时必须保证控制指令（如立即停止任务）的实时性，不能出现因文件上传导致控制指令卡顿的情况。
*   **现有资产**：V4版本《执行机管理-WebSocket通信协议设计.md》。该版本采用了“单WSS连接 + 应用层优先级队列”的方案，试图通过软件逻辑层面的排队来解决阻塞问题。

#### 2. 协作过程
这次修改把“逻辑分离”改成了彻底的“物理分离”。整个过程很清楚地展示了：人负责把控核心架构，Agent负责完善细节。

1.  **现状解读**
    *   我问：“单链接方案在传大文件时，心跳会不会丢？”
    *   Agent分析后确认：会丢。它解释了为什么应用层队列解决不了TCP层的阻塞问题。

2.  **方案讨论**
    *   我给出方向：“那就彻底分开。搞两条WebSocket链接，一条只传指令（Control-Link），一条只传数据（Data-Link）。”
    *   Agent迅速给出了两条新URL的设计建议，并区分了文本和二进制流的处理。

3.  **架构纠偏（关键一步）**
    *   Agent在初版草稿里想偷懒，复用同一个`Endpoint`类，只在内部逻辑做区分。
    *   我指出这样不行：“既然要物理隔离，代码上就得彻底分开。”我要求它设计两个独立的类（`ControlLinkEndpoint` 和 `DataLinkEndpoint`），分别配置不同的线程池和缓冲区大小。Agent随后修正了代码结构。

    > **[截图/视频占位]**：展示对话中“人工纠偏”的过程，即从单类设计到双类设计的Prompt交互截图。

4.  **完善细节**
    *   对于双链接如何关联的问题，Agent补充了时序图：先建立控制链接拿到Token，再建立数据链接带上Token进行绑定。

    > **[截图/视频占位]**：Agent生成的双链接鉴权交互时序图。

#### 3. 最终输出
修订完成的 **V5版《执行机管理-WebSocket通信协议设计.md》**。新设计明确了双端点架构：
*   **Control Endpoint** (`/ws/executor/control`)：配置 2MB 文本缓冲区，保障信令实时性。
*   **Data Endpoint** (`/ws/executor/data`)：配置 10MB 二进制缓冲区，保障大文件吞吐。
这一设计随后被后端代码完整实现，从架构层面彻底消除了数据流阻塞控制流的风险。

#### 4. 实践要点总结
*   **输出标准**：高质量软件实现设计文档。文档应达到**“编码就绪”**深度，具体包含：**静态架构**（精确到类图与方法签名的包结构设计）、**动态流程**（覆盖异常分支的完整时序图）、**接口契约**（字段级的协议/API定义）及**关键决策**（如缓冲区大小、线程模型），确保开发人员能依据文档直接编写代码而无须二次确认。
*   **交叉检查机制**：建立“Agent换角色自查（新对话窗口）”+“人工专家Review”的双重校验流程，确保了文档的严谨性。
*   **人员能力进阶**：要求开发者具备**架构视角的判别力**。Agent 擅长补全细节，但容易生成“逻辑自洽但工程不可行”的方案。只有开发者具备识别系统性风险（如解决 TCP 队头阻塞）的能力，才能在关键节点进行有效纠偏，这是产出高质量设计的核心门槛。
*   **高效配合模式**：遵循**“人定骨架，Agent 填肉”**的原则。开发者不再是文档的撰写者，而是**设计约束的定义者**。高效配合的关键在于：人负责输入核心设计原则（如物理隔离、鉴权逻辑）和验收标准，Agent 负责将这些原则实例化为图表、接口和文字，人机互补达成“1+1>2”。
    > *例如在本案例的文档设计中，**开发者**仅定义了“必须采用双物理链路防止队头阻塞”这一核心骨架；而**Agent**则承担了繁重的“填肉”工作——自动补全了双链路的鉴权交互时序图、设计了具体的 `ControlLinkEndpoint` 与 `DataLinkEndpoint` 类结构、并生成了完整的 JSON 信令定义。这种分工让开发者从枯燥的排版和绘图中解放出来，专注于系统的高可用性设计。*

### 3.2 核心代码生成

#### 1. 输入
*   **设计资产**：
    *   修订后的 V5 版《执行机管理-WebSocket通信协议设计.md》（含双链路架构、JSON/Binary 信令格式及鉴权时序图）。
*   **代码资产**：
    *   项目模块结构：`dialingtest-service` (后端)、`frontend` (前端) 及 `dialingtest-interface` (API定义)。
    *   现有代码基础：`ExecutorMgmtService`（业务逻辑层）及旧版会话管理逻辑。
*   **规范约束**：
    *   API 契约：基于 `dialingtest-interface` 模块 YAML 定义生成的 POJO/DTO。
    *   编码规范：项目内定的 Checkstyle 规则（如 Lombok 使用规范、异常处理标准）。


#### 2. 协作过程
本阶段充分体现了 Agent 在代码生成方面的效率优势，同时也暴露了其在工程化落地方面的局限性。

1.  **上下文注入**
    *   鉴于 Agent 对多模块大型项目（Backend/Frontend/Interface）结构的感知能力有限，开发人员主动注入了项目上下文，明确了后端代码所在的模块路径（如 `dialingtest-service/src/main/java` 及其下的 `controller/executormanagement` 包）。
    *   通过精确的路径指引，Agent 能够准确识别代码生成的目标位置与包命名规范。

2.  **批量生成**
    *   通过 Prompt 指令驱动，Agent 依据设计文档快速生成了 `ControlLinkEndpoint`、`DataLinkEndpoint` 以及 `WebSocketSessionRegistry` 三个核心类文件。
        *   `ControlLinkEndpoint`：负责处理 `/ws/executor/control` 路径，专注于 JSON 文本信令的收发。
        *   `DataLinkEndpoint`：负责处理 `/ws/executor/data` 路径，专注于二进制流的传输，并包含首条消息携带 Token 的鉴权逻辑。
        *   `WebSocketSessionRegistry`：采用双 `ConcurrentHashMap` 结构，分别管理控制链路与数据链路的会话，确保存储的独立性。

        > **[截图/视频占位]**：Agent批量生成Java类文件的IDE界面或对话截图。

3.  **编译排错迭代**
    *   初步生成的代码通常能满足逻辑要求，但在工程编译层面往往存在瑕疵。此阶段的迭代专注于**解决编译错误**，而非业务功能调试。
        *   **问题1：循环依赖**。`ControlLinkEndpoint` 与 `DualLinkRouter` 之间存在双向依赖，导致 Spring 容器启动失败。
        *   **问题2：Lombok 失效**。实体类使用了 `@Data` 注解，但 Maven 编译时未能正确生成 getter/setter 方法。
    *   通过将错误日志反馈给 Agent，它迅速定位并给出了解决方案：利用 `@Autowired` 的 setter 注入解决循环依赖，并修正 `pom.xml` 中的 Lombok 版本配置。问题在数分钟内得到解决，确保代码能够成功编译并启动。

    > **[截图/视频占位]**：展示将编译报错日志投喂给Agent，并获得修复建议的对话截图。

4.  **逻辑完整性迭代**
    *   在编译通过后，进入**实现完整性检查**阶段。利用 Agent 的代码理解能力，进行“自我监察”，确保实现未遗漏设计文档中的关键逻辑。
    *   **处理遗留 TODO**：针对代码量较大的场景，Agent 初次生成往往保留部分 `TODO` 占位符。此阶段需重点扫描此类标记，指令 Agent 继续完成剩余实现。
    *   **执行过程**：在新的对话窗口中，上传设计文档与生成代码，指令 Agent 进行一致性检查：“请检查代码实现是否完全覆盖了文档中定义的所有逻辑？是否存在未实现的 TODO？”
    *   **结果反馈**：Agent 成功识别出代码实现与文档定义存在的差异：“`onClose` 方法仅移除了 Session 对象，未调用 Service 层清理执行机的在线状态资源。”并提示了部分流控逻辑尚为 TODO 状态。
    *   **闭环补全**：经人工确认后，指令 Agent 补全了 `executorMgmtService.handleExecutorDisconnect(token)` 这一关键逻辑及流控代码，确保了业务逻辑的完整闭环。

    > **[截图/视频占位]**：Agent进行“自我代码审查”，指出TODO遗漏项的对话截图。

#### 3. 最终输出
*   **后端**：构建了一套完整的、物理分离的 WebSocket 服务端实现，包含 `ControlLinkEndpoint`（控制）、`DataLinkEndpoint`（数据）和 `WebSocketSessionRegistry`（会话管理），能够正常启动并稳定处理连接。
*   **前端**：生成了配套的 React Hook 组件，能够发起标准的双链接请求。

#### 4. 实践要点总结
*   **文档驱动开发（DDD）**：3.1 节详尽到类名与方法名的设计文档，是实现高效代码生成的基石。文档粒度越细，生成的代码质量越高。
*   **迭代目标分离**：在代码生成阶段，明确将迭代目标限定为 **“编译通过”** 与 **“逻辑完整”**，将复杂的 **“功能验证”** 与 **“业务调试”** 延后至集成测试阶段。这种分离能避免过早陷入细节调试，保持开发节奏的流畅性。
*   **宏观把控，微观提效**：人工聚焦于工程结构校验与依赖管理，将繁琐的协议字段解析与异常处理逻辑交由 Agent 完成，显著提升了开发效率。
*   **主动引导**：Agent 难以自动推断复杂的项目结构，主动注入文件路径与模块信息，能显著减少因路径错误导致的修正成本。
*   **渐进式补全**：面对复杂逻辑生成，接受 Agent 初次生成的“不完美”（如 TODO 占位），通过完整性检查环节驱动 Agent 进行二次补全，是比追求“一次完美生成”更具可行性的策略。

1.  **环境构建（AI 辅助 Infrastructure as Code）**
    *   **选型考量**：面对微服务架构，我决定采用“Python 脚本 + Docker 容器”的轻量级方案，能很容易构造出隔离的测试环境。
    *   **配置生成**：我指令 Agent：“请为当前项目生成一个 `docker-compose-test.yml`，包含 PostgreSQL 和后端服务，并提供一键启动脚本。” Agent 迅速生成了包含环境编排、数据库初始化（`init.sql`）及端口映射的完整配置，极大地提升了环境搭建效率。

2.  **批量生成测试代码**

    *   解决方案：Agent 在测试代码中引入了 `wait_for_condition` 轮询机制，替代了硬编码的 `time.sleep(1)`，既保证了测试稳定性，又提升了执行效率。

*   **完整的集成测试套件**：位于 `test/executormanagement/` 目录下，包含覆盖核心业务的 Python 测试脚本。
*   **自动化验证能力**：
    *   **双链接生命周期**：验证了从建立、认证、绑定到断开、重连的全生命周期。
    *   **异常容错**：覆盖了 Token 错误、链路单边断开、重复连接等异常场景。

*   **异构技术栈红利**：在 Java 微服务项目中，大胆引入 Python 作为测试开发语言。利用 Python 极其灵活的脚本能力和 Docker 的环境编排能力，能以极低的成本构造出这就绪（Ready-to-use）的集成测试环境。
*   **复用降低复杂度**：得益于前期 `DualWebSocketClient` 的封装，测试用例代码非常简洁，专注于业务断言而非网络细节。
*   **真实环境集成**：集成测试应尽量避免 Mock，直接与数据库交互能发现更多状态同步类 Bug。
*   **异步测试策略**：对于涉及网络与数据库状态同步的场景，必须采用轮询等待（Polling Wait）机制，而非固定延时，以适应不确定的系统响应时间。

## 第四章：模式转变 —— Agent模式 vs 传统开发的深度对比

本章深度剖析编码 Agent 引入后，软件开发模式在流程、角色和认知层面发生的本质变化。尽管“设计-编码-测试-调试”的经典软件工程阶段没有改变，但每个阶段的执行逻辑与重心已截然不同。

### 4.1 全景对比：从“手工作坊”到“人机流水线”

| 维度 | 传统开发模式 | Agent 辅助开发模式 | 核心差异点 |
| :--- | :--- | :--- | :--- |
| **1. 需求与设计** | **全手工制作**。开发者需亲自编写文档字句、绘制时序图、定义 JSON 结构。容易因繁琐而偷懒，导致文档滞后于代码。 | **人定骨架，Agent 填肉**。开发者定义核心架构（如“双物理链路”），Agent 补全细节（如时序图、API 定义）。 | **文档即代码的前置**。文档不仅是给人看的，更是生成代码的“超强 Prompt”。文档质量直接决定代码生成的质量。 |
| **2. 编码实现** | **逐行编写**。需关注语法细节、IDE 配置、样板代码（Boilerplate）。大量时间花在 CRUD 和查阅 API 上。 | **批量生成 + 迭代纠偏**。注入上下文后，Agent 批量生成核心类。开发者的工作重心从“写”变成了“审”和“修”（如解决循环依赖、Lombok 版本问题）。 | **实现门槛降低，审核门槛升高**。不再需要手写每一行，但需要一眼看出 Agent 生成的代码在工程上是否可行（如架构判别力）。 |
| **3. 测试设计** | **往往被忽视**。测试用例编写耗时，常依赖人工点点点，自动化覆盖率低。 | **辅助发散 + 框架生成**。Agent 扫描代码分析边界条件（如“网络抖动”），并能快速封装测试工具类（如 `DualWebSocketClient`）。 | **测试左移**。利用 Agent 快速生成测试脚手架和异构语言（Python 测 Java）的测试代码，让自动化测试成本大幅降低。 |
| **4. 调试与运维** | **经验驱动**。靠开发者个人经验分析日志，搜索 StackOverflow。 | **全栈关联分析**。将跨语言（Java后端+Python测试端）的日志投喂给 Agent，由 Agent 关联分析定位 Bug（如签名算法差异）。 | **日志即 Prompt**。不再人工概括错误，而是直接利用原始日志让 AI 还原现场。 |

#### 【角色画像重构】
基于上述流程变化，开发者的核心职能发生了根本性迁移：
*   **从“撰写者”到“定义者”**：不再纠结于文档排版，而是专注于**架构决策**与**边界约束**的定义。
*   **从“工匠”到“监工”**：不再以逐行编码为荣，而是以快速**Review**、识别“幻觉”与工程隐患为核心竞争力。
*   **从“单栈开发”到“全栈指挥”**：利用 Agent 抹平语言差异，指挥 Python/Docker 脚本进行全栈验证。
*   **从“经验排查”到“证据整合”**：调试不再靠猜，而是靠收集全链路日志，驱动 AI 进行推理。

### 4.2 核心差异：“认知负债”与效率瓶颈的转移

Agent 模式极大提升了生产力，但也引入了一个隐形陷阱——**“认知负债”（Cognitive Debt）**。

#### 1. 认知逆差：生成先于理解
*   **差异**：传统模式下，理解是生成的先决条件，代码是思维的产物。而在 Agent 模式下，**生成跑在了理解前面**。Agent 可以在 10 秒内生成 500 行逻辑严密的代码，而人类完全理解这些代码可能需要几十分钟甚至几个小时。
*   **后果**：若不刻意去阅读和理解，这部分代码对开发者就是“黑盒”。随着项目推进，黑盒累积，维护难度将呈指数级上升。

#### 2. 集成测试的新意义：Agent时代的“防腐层”与“说明书”
如果说以前集成测试是“锦上添花”，那么在 Agent 模式下它就是**“救命稻草”**。
*   **行为契约**：当代码非己所出时，**测试用例即是文档**。通过阅读测试脚本，维护者能立刻明白系统的核心契约，无需深究实现细节。
*   **重构底气**：没有集成测试的 Agent 生成代码，是一次性的**“抛弃型代码”**。只有拥有覆盖完善的黑盒测试，开发者才敢让 Agent 进行二次修改，防止“蝴蝶效应”。

#### 3. 效率瓶颈：学习能力的再定义
**“现在的效率瓶颈，不再是编码速度，而是开发人员自身的学习和理解能力。”**
*   **应对策略 A - 锚点回归**：设计文档（如《WebSocket通信协议设计.md》）不再是形式主义，它是理解代码的“地图”。维护时先回看设计文档，而非直接扎进代码堆。
*   **应对策略 B - 调试即学习**：利用 Bug 修复的过程（如让 Agent 分析日志），强迫自己去理解生成代码的细节，建立大脑索引。
*   **应对策略 C - 维护模式变更**：对于不熟悉的代码，不再尝试手动“微修”，而是通过描述问题让 Agent 去修，并利用集成测试进行验证。开发者的角色从“修表匠”（精细操作）变成了“工厂主”（管理流水线）。
