  1. 原始需求：CloudUDN拨测需实现控制流与数据流分离，建立双WebSocket链接以避免大数据阻塞控制指令。
  2. 现有资产：V4版本《执行机管理-WebSocket通信协议设计.md》。
- **人机协作过程**：
  1. **现状解读**：用户上传V4版协议文档，要求Agent深度解析现有方案；Agent梳理出当前单链路在传输大文件时可能阻塞心跳和控制指令的隐患。
  2. **方案研讨**：用户提出“双链接、数控分离”的核心需求；Agent分析修改点，建议拆分为Control-Channel和Data-Channel，并列出协议变更清单；双方经过多轮对话对齐了Session管理细节。
  3. **初次执行**：Agent基于讨论结果修订设计文档；修改完成后，用户开启新对话窗口，指令Agent对新文档进行质量检查（Review），同时自己进行人工审查。
  4. **关键纠偏**：用户敏锐发现Agent的初版设计采用了“单物理连接复用逻辑通道”的方案，指出现实中仍会存在TCP队头阻塞问题，违背了“物理隔离”初衷；用户指令Agent将设计调整为两条独立的物理TCP连接。
  5. **迭代完善**：Agent重新修正时序图与连接建立流程，明确区分两个WebSocket Endpoint；用户与Agent再次进行双重检查，确认逻辑无误后定稿。
- **输出标准**：
  1. 逻辑自洽：彻底解决数据阻塞控制问题，双链路物理分离。

- **最终输出**：修订完成的《执行机管理-WebSocket通信协议设计.md》，包含独立的控制与数据通道定义、双重鉴权及异常处理流程。

### 3.2 核心代码生成
<!--
- **输入**：
  1. 设计文档：修订后的《执行机管理-WebSocket通信协议设计.md》（协议细节已完全确定）。
  2. 引导信息：项目根目录结构、模块划分（Controller/Service/Entity）、现有依赖版本（Spring Boot 2.7.x）。
- **人机协作过程**：
  1. **上下文注入**：鉴于Agent对大型项目结构的感知局限，用户主动提供项目根目录路径，指引Agent定位至`dialingtest-service`模块。
  2. **批量生成**：Prompt指令“基于设计文档，实现WebSocket双通道Handler及SessionManager”，Agent一次性生成了服务端处理逻辑、心跳机制及前端React Hook。
  3. **编译/启动排错**：
      *   用户尝试启动应用，遇到Bean循环依赖与Lombok注解失效问题。
      *   用户直接粘贴报错日志到对话框。
      *   Agent分析日志，快速给出“拆分Configuration类”与“修正pom.xml依赖scope”的修复补丁。
  4. **实现一致性验收**：
      *   代码生成量较大，人工逐行Review效率低。用户采取策略：**宏观人工审查 + 微观Agent验收**。
      *   **人工审查**：重点检查新引入的第三方库（如WebSocket依赖）版本是否冲突、项目层级结构是否乱套。
      *   **Agent验收**：开启新对话窗口，上传新生成的代码文件与原始设计文档，Prompt要求“检查代码实现是否完全覆盖了文档中的所有协议字段与流程”。
      *   Agent反馈：指出代码中漏掉了“断连时的资源清理逻辑”，用户随即指令补全。
- **输出标准**：
  1. 零编译错误：代码无语法问题，服务正常启动。
  2. 协议一致性：代码逻辑严格对应设计文档中的每一个信令交互。
- **最终输出**：
  1. 后端：稳定运行的WebSocket服务端（Handler, Service）。
  2. 前端：可用的React连接状态组件。

> *   **演示场景1：一次性生成的震撼**
>     *   *素材*：代码Diff截图 —— 展示Agent一次性生成数百行核心业务代码的壮观场面（体现文档完备带来的代码生成高效率）。
> *   **演示场景2：实现一致性检查**
>     *   *素材*：验收对话截图 —— 展示Agent指出“代码漏掉资源清理逻辑”的对话片段，证明Agent进行“自我监察”的可行性。
>
> **【实践要点总结】**

> *   **分层审查策略**：面对大量生成代码，人工聚焦“工程结构与依赖”，Agent聚焦“逻辑细节与协议覆盖”，实现效率最大化。
> *   **引导式上下文**：主动提供项目路径与模块结构，有效弥补了当前工具在大型项目索引上的短板。
