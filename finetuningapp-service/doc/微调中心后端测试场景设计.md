## 1. 测试概述

### 1.1 测试目标

验证 `finetuningapp-service` 作为微调业务执行引擎的核心能力，重点保障**分布式任务调度**的正确性、**Kafka 历史数据回放**的准确性以及与外部系统（拨测中心）的**异步交互**稳定性。

**MVP阶段核心目标**：
跑通从“任务提交”到“结果产出”的闭环流程，验证系统骨架的可用性。

### 1.2 测试范围 (MVP)

## 2. 核心测试场景

### 2.1 FT-01: 预处理任务 E2E 测试 (Preprocess Pipeline) ⚠️ MVP核心

**测试目标**：验证从拨测中心提交任务到 Kafka 数据回放、清洗并生成结果的全链路逻辑。

**前置条件**：
1. **Kafka环境**：`topic-raw-flow` (Protobuf输入) 和 `topic-labeled-sample` (JSON输出) 已创建。
2. **数据预置**：在 `topic-raw-flow` 中写入特定时间段（T1~T2）、特定 `UE_ID` 的 Protobuf 历史数据。
   - 数据应包含：符合清洗规则的有效流（应被保留）和不符合规则的噪声流（应被过滤）。
3. **Mock服务**：启动 Mock Callback Server 用于接收任务完成通知。
4. **环境配置**：配置 `finetuningapp-service` 的回调地址（如通过环境变量 `APP_DIALING_SERVICE_URL`）指向 Mock Callback Server。

**测试步骤**：
1. **提交任务**：
   - 调用北向 API `POST /tasks/preprocess`。
   - 参数指定：`ue_id`、`time_range` (覆盖T1~T2)。
2. **验证入列**：
   - 查询数据库 `t_finetuning_task` 表。
   - 验证任务状态为 `PENDING`。
3. **触发调度**：
   - 等待 TaskPoller 周期性扫描（或观察日志确认抢占）。
   - 验证数据库状态流转为 `RUNNING`，`worker_instance` 更新为当前节点 IP。
4. **执行验证 (系统自动执行)**：
   - Worker 基于 `UE_ID` 计算 Partition 并 Seek 到 T1 时刻。
   - Worker 读取数据直到 T2 时刻。
   - 内存引擎根据默认规则或覆盖规则进行流量清洗。
5. **验证产出**：
   - **Kafka输出**：订阅 `topic-labeled-sample`，验证是否收到了预期数量的 JSON 格式样本，且 `ue_id` 匹配。
   - **回调通知**：检查 Mock Callback Server 是否收到 `POST` 请求，校验 `status=SUCCESS` 和 `async_job_id`。
6. **最终状态**：
   - 验证数据库任务状态最终变更为 `SUCCESS`。

**验证点**：
- ✅ **任务调度**：状态正确流转 (PENDING -> RUNNING -> SUCCESS)。
- ✅ **数据回放**：能精确 Seek 到指定时间点，不回放无关时间段的数据。
- ✅ **数据清洗**：
  - 噪声数据被过滤（如流量过小）。
  - 有效数据被保留并转化为 JSON 格式。
- ✅ **异步回调**：正确回调给上游系统，携带任务结果。

**错误场景 (可选)**：
- **回放无数据**：指定时间段内 Kafka 无数据 -> 任务应成功结束但产出为空。
- **回调失败**：Mock Server 不可用 -> 任务状态可能记录回调失败日志，但业务状态仍为 SUCCESS (取决于重试策略)。

## 3. 验证清单

### 3.1 功能验证

| 功能模块 | 验证项 | 预期结果 |
| :--- | :--- | :--- |
| **北向接口** | 任务提交 API | 返回 TaskID，HTTP 200 |
| **调度模块** | 任务抢占 | 多实例下仅一个 Worker 抢占成功 (需多实例环境，MVP可简化) |
| **Kafka回放** | Offset 定位 | 准确从 StartTime 对应的 Offset 开始消费 |
| **内存清洗** | 规则过滤 | 能够根据 `min_packet_count` 等规则过滤数据 |
| **结果输出** | 序列化 | 输出合法的 JSON 格式样本 |

### 3.2 技术验证

| 技术项 | 验证内容 | 标准 |
| :--- | :--- | :--- |
| **Protobuf** | 反序列化 | 能正确解析 C++ 写入的二进制流 |
| **异步回调** | HTTP Client | 能正确发起 POST 请求并处理响应 |

## 4. 测试数据要求

### 4.1 Kafka 预置数据

需要构造符合 `RawFlowMsg` Protobuf 定义的二进制消息：
- **Case A (有效数据)**: `ue_id="test-ue-01"`, `timestamp=T`, `packet_count=100` (大于阈值)。
- **Case B (噪声数据)**: `ue_id="test-ue-01"`, `timestamp=T+1s`, `packet_count=5` (小于阈值)。

### 4.2 数据库配置

- `t_cleaning_rule` 表中需存在默认规则配置，或在任务提交参数中直接携带 `config` 进行覆盖。
